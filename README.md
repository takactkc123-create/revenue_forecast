# 個人住民税予測モデル

## 概要
自治体におけるデータベースから過去の税額情報を取得し、翌年の税収を予測するモデル

### 課題

住民税は自治体の主要財源であり、翌年度の税収をどれだけ正確に見通せるかが予算編成の精度に直結する。既存の集計データにトレンドを補正した予測では、`予測精度`・`区間推定`・`税制改正`などの対応が課題となっている。

### 目的

個人の収入・控除情報をもとに翌年度の住民税額を予測し、自治体全体で積み上げて税収見込み額（95%信頼区間つき）を算出することで、より正確な予測を算出することを目的とする。

### 手法
個人の収入・控除情報をもとに翌年の住民税額を予測する機械学習モデルを構築するパイプラインである。LightGBM（勾配ブースティング）を用いて個人レベルの税額を推定し、それを集計することで自治体全体の税収見込みを算出する。

実務では実データをもとにプログラムを実行するが、GitHub にはダミーデータ生成機能を追加し、その出力データを元にプロジェクトを実行している。

## 本プロジェクトの役割

| 項目 | 内容 |
|---|---|
| 位置づけ | 予算編成での税収見込み算出を補助する**支援ツール**。出力（個人別予測・信頼区間・自治体合算値）は参考値であり、税額の決定・徴収は既存の税務基幹システムが担う |
| 対象範囲 | 個人住民税（均等割＋所得割）の翌年度税収予測に限定 |
| 処理の流れ | 基幹系から抽出した個人別の収入・控除データ（`01_src_sql/00_CsvCreate.sql`）を起点に、特徴量エンジニアリング→学習→翌年予測→マクロ補正→可視化。最終出力は「自治体全体の翌年度税収見込み額（信頼区間つき）」 |
| ダミー版の役割 | 実データがない段階でもパイプライン全体と精度検証手法を確認できるPoC用途。全国統計に基づく疑似データで代替 |
| 実データ版の役割 | 基幹系データを投入する本番想定。列名・控除計算式を実データに置き換える。控除をフラグでしか持たない場合は金額化の加工を追加（`03_feature_eng.py`） |
| 前提と限界 | 過去の実績パターンの学習に基づく。税制改正・急激な経済変動は`tax_reform.py`の`REFORMS`等の手動補正でカバーする。 |

## 結果の概要

> 詳細な検証条件・全指標は「[ダミーデータでの結果](#ダミーデータでの結果)」「[実データでの検証結果](#実データでの検証結果)」を参照。

| | 使用モデル | 検証データ規模 | 2026年度 税収予測 | 前年比 | 集計誤差率（テスト年2025）<br>モデル単体／本番と同じ方法 | 備考 |
|---|---|---|---:|---:|---:|---|
| ダミーデータ検証 | LightGBM（勾配ブースティング木） | 597,000件（6年分） | 244.85億円 | +7.01% | +0.01%／−0.25% | `06`の補正後。95%信頼区間 [236.10〜253.60] 億円（過去年検証の年ごとのぶれから算出）／WMAPE 0.53% |
| 実データ検証 | 同上 | 約1,340,000件（6年分） | 非公開 | +4.91% | +0.61%／未検証 | WMAPE 6.25%／個人単位の誤差（RMSE・R²）はダミーより大きいが、自治体全体の集計精度は既存ツールより向上した |

> 集計誤差率の「モデル単体」は、検証年の本当の特徴量で予測した誤差。「本番と同じ方法」は、`05`と同じく前年までのデータで学習し、前年のデータを外挿した特徴量で予測した誤差（過去年検証。ダミーの2022〜2025年の平均は −0.41%）。

- LightGBMで個人ごとの翌年度住民税額を予測し、自治体全体で積み上げることで、高精度に翌年度税収見込みを算出することが目的のモデルである。
- 個人単位の予測誤差は高所得層等の外れ値に引っ張られやすいが、自治体が最終的に必要とする「税収合計」への影響は限定的である（多くの誤差が相殺されるため）。
- 実データでも、非課税判定（地方税法295条）による強制0円補正や上限パーセンタイルでのクリップなど、税制ルールベースの後処理と組み合わせることで集計精度を担保している。

## 選定モデル

> LightGBM（勾配ブースティング木）

| 観点 | 内容 |
|---|---|
| 税額の計算が階段状 | 所得控除・非課税基準（地方税法295条）は「ある所得を境に切り替わる」構造。決定木は分割でそのまま表現でき、線形回帰のように閾値ごとの特徴量を人手で作る必要がない |
| 前処理が少ない | 分割は値の大小だけで決まるため、説明変数の対数変換や標準化が不要。自治体ごとに分布が違っても扱いやすい |
| 実データとの相性 | 基幹系DBからの抽出データは全項目が数値（性別・寡婦・障害者等もコード化済み）で、そのまま入力できる |
| 外れ値への耐性 | 高額納税者は個人単位の誤差（RMSE・WMAPE）を押し上げるが、主指標の集計誤差率への影響は小さい |
| 業務の引継 | 人事異動に伴う引継ぎにおいて、極力シンプルなデータ加工とモデル選定で運用することが望ましい |

## 実行方法

モデルの実行（学習・予測・補正・グラフ出力）はCLI版（`02_src_py/`）で行う。Notebook版（`03_notebooks/`）は、GitHub上で各ステップの処理内容と出力（表・グラフ）をそのまま読めるように置いている公開用である。

### 注意（`02_src_py/` と `03_notebooks/` の役割）

| | `02_src_py/`（CLI版） | `03_notebooks/`（Notebook版） |
|---|---|---|
| 役割 | モデル実行の本体（**原本**） | GitHub公開用。処理内容と実行結果（表・グラフ）を閲覧するために置いている |
| `config.py`・`tax_reform.py` | 原本 | 原本のコピー。ノートブックだけを取り出しても動くよう同じフォルダに置き、各ノートブックの先頭のセルで読み込み先に追加している |
| 変更するとき | ここを編集する | 原本を変えたあと、`config.py`・`tax_reform.py`をコピーし、ノートブックの該当セルにも同じ変更を入れ、上から実行し直して出力を更新する |

- 設定値やコードは必ず`02_src_py/`の原本を編集する。`03_notebooks/`だけを直すと、実行に使うCLI版に反映されないため注意。

### CLI版（`02_src_py/`）

```bash
# 実データがある場合（03から開始）
uv run python 02_src_py/03_feature_eng.py
uv run python 02_src_py/04_model_train.py --retrain-all   # walk-forward検証 + 全年再学習
uv run python 02_src_py/05_predict_2026.py
uv run python 02_src_py/06_trend_correction.py
uv run python 02_src_py/07_visualize.py

# ダミーデータで試す場合（01から開始）
uv run python 02_src_py/01_generate_dummy.py
uv run python 02_src_py/03_feature_eng.py
uv run python 02_src_py/04_model_train.py --retrain-all
uv run python 02_src_py/05_predict_2026.py
uv run python 02_src_py/06_trend_correction.py
uv run python 02_src_py/07_visualize.py
```

Windows PowerShellでも同じコマンドがそのまま使用可能

`02_src_py/`の中から実行する場合は、フォルダ名を除いて`uv run python 06_trend_correction.py`のように指定する。

### Notebook版(`03_notebooks/`)での実行

`03_notebooks/`配下に、各スクリプトと同一ロジックのJupyter Notebook版（`01_generate_dummy.ipynb`〜`07_visualize.ipynb`）を公開用として置いている。保存されている出力は、CLI版と同じ結果になることを確認して実行したもの。手元で実行して確かめることもできる。CLI版との違いは以下の通り。

- `main()`に集約せず、関数定義・実行・結果表示・保存をセル単位に分割しており、上から順に実行すると各ステップの出力（表・グラフ）がコード直下に表示される。
- CLI引数（`--walkforward`, `--year`等）に相当する設定は、各ノートブック内の`NOTEBOOK_ARGS`セルで指定する（`NOTEBOOK_ARGS = ["--retrain-all"]`のようにCLIと同じ文字列を並べる）。
- `04_model_train.ipynb`は、このREADMEに載せている結果と同じになるよう`NOTEBOOK_ARGS = ["--retrain-all"]`を設定済み。
- `03_notebooks/`から開いてそのまま実行してもプロジェクトルート基準の相対パスが解決できるよう、各ノートブックの先頭で自動的にカレントディレクトリをルートへ戻す処理が入っている。VS Code等で開く場合は`.venv`（`2026-chotei-01`）をカーネルに選択すること。

### 検証条件

| 項目 | 内容 |
|---|---|
| データ種別 | ダミーデータ（`01_generate_dummy.py`生成、全国統計ベース） |

### 評価指標（TRAIN in-sample / ウォークフォワード最終フォールド TEST out-of-sample）

| 指標 | 意味・式 | TRAIN（2020〜2025 in-sample） | TEST（fold4: train=2020〜2024→test=2025） | 備考 | 位置づけ |
|---|---|---|---|---|---|
| 集計誤差率 | 合計のズレの割合<br>（予測合計−実績合計）÷実績合計 | -0.00% | +0.01% | 符号付きのため、個人ごとの誤差のプラス・マイナスが打ち消し合う |（**主指標**）税収見込みの精度そのもの |
| WMAPE | 円で重み付けした誤差率<br>Σ\|誤差\|÷Σ実績 | 0.48% | 0.53% | 非課税者含む。集計誤差率の上限（全員が同じ向きに外れた場合に一致） |（第2指標）円ベース：税収のうち何円分を個人に誤って割り振ったか。高額納税者の外れは税額に比例して効く |
| MAPE | 1人ずつの誤差率の平均<br>平均(\|誤差\|÷実績) | 1.59% | 1.38% | 課税者のみ（実績0円は分母にできないため除外） |（参考）人数ベースで、一般の納税者1人ひとりの当たり具合。少額納税者の外れで大きくなり、非課税者の誤予測は反映されない |

### 所見・特記事項
- ダミーデータを用いた結果と比べて精度が低いことが伺える。ダミーデータが正規分布に近い形状であるのに対し、実データは特定区間の偏りや外れ値が顕著であったことが主な原因と考えられる。個人単位の精度は誤差が大きいものの、本プロジェクトの目的である、税収の予測から鑑みると、集計誤差率の精度としてはダミーデータ同等の精度を保つことができていると読み取れる。
- 一定数極端に税額が大きい納税者（詳細は非公表）が存在するため、多少の予測誤差が発生する。その上で学習精度のために、実データのみパーセンタイルでクリップし、値を丸めるなどのデータ加工を実装した。その影響で`05`の予測の集計結果が実データの結果より過小になったことが伺える。ただし、少数の高額納税者については、単年の高額所得の可能性や、転出・死亡による翌年の税収0円等の可能性を考慮すると、前年データをそのまま予測に用いるよりはリスクを抑えられることから、学習段階でのデータの上限設定は有効と考える。

### 実データにおける取り組み
> 各団体によって人口推移、所得平均、分布等が異なるため、部分的なカスタマイズ処理は必要である。下記は一例。

#### ダミー版との主な相違点

| 項目 | ダミー版（`02_src_py/`） | 実データ版 |
|---|---|---|
| 所得列 | 全国統計ベースで生成した個別所得列。`03`で合計して`総所得金額等`を作る | 抽出データに合計所得の列が既にあるためそのまま使用 |
| 障害者・寡婦・配偶者・扶養控除 | 金額列として生成 | 抽出データはコード値・人数で持つため、`03`で住民税の控除額表に基づき金額へ変換 |

#### 今後の課題

- 2026年予測では、対象者を2025年と同じ人・同じ人数とし、全員を継続者として扱っている（死亡・転出・転入と加齢は反映していない）。ダミー版で「伸び率を継続者ベースにする＋入れ替わり補正」「年齢を1歳進める」を試算したが、過去年検証の誤差は小さくならなかったため見送った。実データは検証中。
- 2024年定額減税による税収への影響について、本モデルでは定額減税前の税額に戻して学習している。今後同様の税制改正における`tax_reform.py`の精度検証が必要。
- 所得上位数%の高額所得者の細分化。所得別の翌年継続率（給与なら継続確率高、分離所得なら低等の仮説）を把握し、誤差を反映する等の対応が必要。

LightGBM で個人の年税額を学習・検証する。予測値は、課税者は均等割を下限にし、非課税基準に該当する人は0円に上書きする。

| オプション | 動作 |
|---|---|
| `--standard`（既定） | `TRAIN_YEARS` で学習し、`TEST_YEAR` で評価（1回のホールドアウト） |

| `--retrain-all` | walk-forward で検証したあと、全年で再学習（運用時の推奨。このREADMEの結果） |

- 主指標は集計誤差率（予測合計と実績合計の差）。各指標の意味は「[ダミーデータでの結果](#ダミーデータでの結果)」の評価指標の表を参照。
- `year` は特徴量に含めない（木モデルは学習範囲外の年を外挿できないため）。予測年の所得の伸びは`05`の外挿で与える。

### 年度を更新したいとき

毎年の運用で必ず行う。`config.py`の年度を1年ずつ進める。


あわせて次を確認する。

1. 税制改正があった年度は、`tax_reform.py`冒頭の年度別の表に施行年度の行を足す（「[税制改正に対応したいとき](#税制改正に対応したいとき)」）。
2. 伸び率の方式を table にしている場合は、`FORECAST_GROWTH_TABLE`に新しい予測年度の値を足す（欠けているとエラーで止まる）。
3. ダミーデータを作り直す場合は、`POPULATION_GROWTH_RATES`・`SALARY_GROWTH_RATES`・`PENSION_GROWTH_RATES`に新しい年を足す。

### 予測の伸び率を指定したいとき（春闘・年金改定率など）

`05`が直近年の所得を伸ばすときの伸び率は、既定では実績から自動で決める。外部の値を使うとき、または伸ばさないときは次のように指定する。

| 方式 | 指定方法 | 内容 | `06`の自動のトレンド補正 |
|---|---|---|---|
| auto（既定） | `config.py`の`GROWTH_SOURCE = "auto"` | 実績の全員平均の直近2年の伸び率（給与・年金・事業所得） | 掛ける |
| table | `GROWTH_SOURCE = "table"`または`--growth table` | `FORECAST_GROWTH_TABLE`の値（給与・年金。事業所得は自動） | 掛ける |
| none | `GROWTH_SOURCE = "none"`または`--growth none` | 伸び率0%（直近年の所得のまま） | 掛けない |
| 直接指定 | `--wage-rate 0.0525`・`--pension-rate 0.019`（上乗せは`--wage-delta`） | 方式より優先する | 掛けない |

```python
# config.py（キーは住民税の年度、値は前年の所得の伸び率。例: 2026年度 ← 2025年の春闘）
GROWTH_SOURCE = "table"
FORECAST_GROWTH_TABLE = {
    "給与収入":          {2022: ..., 2023: ..., 2024: ..., 2025: ..., 2026: ...},
    "雑収入_公的年金等": {2022: ..., 2023: ..., 2024: ..., 2025: ..., 2026: ...},
}
```

- table では、予測年度に加えて過去年検証の年度（2022〜2025）の値も要る。`06`の乗率と信頼区間は、本番と同じ方式で行った過去年検証から作るため。
- 方式を変えたら、`05`を`--no-backtest`なしで実行し直す（方式が一致しないと`06`は自動の乗率を掛けず、理由を表示する）。
- 使った方式と伸び率は`05out_prediction_summary_YYYY.csv`に残る。表の値は既定で空で、実際の値と出典は運用で決める。

全く補正しない場合は、`05 --growth none`と`06 --no-trend`を組み合わせる（税制改正の補正は既定で無効）。

### 税制改正に対応したいとき

改正の種類によって書く場所が違う。同じ改正を両方に書くと二重に適用される。

| 改正の種類 | 書く場所 | 例 |
|---|---|---|
| 恒久的な改正（金額・基準が変わる） | `tax_reform.py`冒頭の年度別の表に、施行年度の行を足す | 給与所得控除の最低額（2026年度〜65万円）、均等割、非課税基準 |
| 期間限定の補正、個人データでは表せない改正 | `tax_reform.py`末尾の`REFORMS`に辞書を1つ足す | 定額減税（2024年）、扶養要件の引き上げ（`06`の集計補正） |

`REFORMS`に足すときの手順:

1. 新しい計算が必要な場合だけ、`tax_reform.py`に補正関数（`_apply_<name>`）を書く。
2. `REFORMS`に辞書を1つ足す。

```python
{
    "name": "teigaku_reduction",          # 識別子
    "func": _apply_teigaku_reduction,     # 補正関数（06 の集計補正は None）
    "reform_type": "label_correction",    # 04で学習ラベル / feature_correction=05で特徴量 / macro_correction=06で集計値
    "effective_year": 2024,               # 施行年度
    "one_time": True,                     # True=施行年のみ
    "active": False,                      # False なら補正しない
    "params": {"amount_per_person": 10_000},
    "memo": "備考",
},
```

3. `uv run python 02_src_py/tax_reform.py`を実行し、記録（`models/tax_reform_snapshot.json`）を更新する（忘れると`04`が警告する。結果には影響しない）。

### 特徴量を追加・削除したいとき

モデルに使う列は`config.py`の2つの一覧で管理し、`FEATURE_COLS`はその2つをつないだもの。

```python
# config.py
RAW_FEATURE_COLS = [...]        # 元データにある列のうち、モデルに使うもの
GENERATED_FEATURE_COLS = [...]  # 03_feature_eng.py の preprocess() が作る列
FEATURE_COLS = RAW_FEATURE_COLS + GENERATED_FEATURE_COLS
```

| やりたいこと | 直す場所 |
|---|---|
| 元データにある列を使う・外す | `RAW_FEATURE_COLS`に書き足す・消す |
| `03`で新しい列を作る | `preprocess()`に処理を書き、`GENERATED_FEATURE_COLS`にも同じ列名を書き足す |
| `03`で作っている列を外す | `preprocess()`の処理と`GENERATED_FEATURE_COLS`の両方から消す |

- `03`は、`GENERATED_FEATURE_COLS`と実際に作った列がずれているとエラーで止まる（片方だけの直し忘れを防ぐため）。
- 変更後は`03`→`04`→`05`を実行し直す。

### その他の設定（補足）

| やりたいこと | 設定 |
|---|---|
| 予測年の人口の増減を反映する | `06 --factor 0.988`（テスト年より1.2%減る想定）。指定すると自動のトレンド補正は使わない |
| 検証モードの既定を変える | `config.py`の`VALIDATION_MODE`（既定`"standard"`。このREADMEの結果は`--retrain-all`） |

## 注意事項

- GitHubで公開しているのはダミーデータ版であり、掲載している実データの検証結果は評価指標と誤差率のみを示している。実際の税収予測に使用する際は、実データによる再学習と十分な検証を行うこと。
- 住民税の計算式は自治体・年度によって一部異なる場合がある（級地区分による非課税ラインの違い、均等割の超過課税等）。ダミー版は所得割の標準税率（10%）、1級地の非課税範囲、超過課税を含む均等割（5,300円）を前提としている。自治体に合わせるときは`tax_reform.py`冒頭の年度別の表を直す。
- 個人情報を含む実データを扱う場合は、データの取扱いポリシーに従うこと。`data/`・`models/`フォルダはこの理由から常に`.gitignore`対象とし、GitHubには公開しない。
