# 個人住民税の税収予測モデル（LightGBM）

個人ごとの収入・控除データから翌年度の住民税額を LightGBM で予測し、積み上げて**自治体全体の税収見込み（95%信頼区間つき）**を算出するパイプライン。
実務では実データで運用しており、このリポジトリでは全国統計をもとに生成したダミーデータで同じ処理を再現している。

**使用技術**: Python / LightGBM / pandas / scikit-learn / scipy / matplotlib / Jupyter / uv

---

## 背景と課題

- 住民税は自治体の主要財源で、翌年度の税収見込みの精度が予算編成の精度に直結する。
- 集計値にトレンドを掛ける従来の方法では、予測の精度・不確かさの幅（区間推定）・税制改正への対応に限界があった。
- そこで、個人単位で翌年度の税額を予測して合算し、税法のルールはモデルの外で確実に処理する仕組みを作った。

**役割・期間**：2026年7〜10月。企画は所属部署の職員と2人で行い、開発は1人で担当。

## モデルの実行結果

![2026年度の税収予測](05_results/fig6_税収推移と予測_2026.png)

| | 集計誤差率（テスト年2025） | WMAPE | 2026年度の予測 | 
|---|---:|---:|---|
| ダミーデータ（597,000件・6年分） | +0.01% | 0.53% | 244.85億円（前年比 +7.01%、95%信頼区間 236.10〜253.60億円） |
| 実データ（6年分） | +0.61% | 6.25% | 税額非公開 |

- **主指標は集計誤差率**（予測合計と実績合計の差）。実データでは、従来のツールより税収合計と予測の誤差が約1/3に減少し、精度が向上した。
- 実データは個人単位の誤差がダミーより大きいが、個人ごとの誤差の多くは相殺されるため、税収合計の精度は保たれている。
- ダミーの精度が非常に高いのは、税額を特徴量と同じ計算式から作っているため。実データの金額・件数は非公開とし、精度の比率だけを載せている。
- 2026年度の予測と同じ手順で過去4年を予測し直した検証（過去年の検証）では、**ダミーデータ**の集計誤差率は平均 -0.41%（年ごとのぶれは標準偏差 1.00%）。この平均を補正に、ぶれを95%信頼区間に使っている。

**【ダミーデータ】過去年の検証**

| 予測した年度 | 学習に使った年度 | 予測に使った所得 | 実績との誤差 |
|---|---|---|---:|
| 2022 | 2020〜2021 | 2021年度の所得から推計 | +0.89% |
| 2023 | 2020〜2022 | 2022年度の所得から推計 | -1.49% |
| 2024 | 2020〜2023 | 2023年度の所得から推計 | -0.79% |
| 2025 | 2020〜2024 | 2024年度の所得から推計 | -0.25% |
| **予測対象** 2026 | 2020〜2025 | 2025年度の所得から推計 | （ダミーの作成は2025年までのため予測のみ） |

**【実データ】実運用の結果**

| | 予測の条件 | 集計誤差率 |
|---|---|---:|
| テスト（実データ・2025年度） | 2025の本当の所得・控除で予測（walk-forward） | +0.61% |
| 実運用（実データ・2026年度） | 2025の所得・控除から推計して予測し、2026年6月30日時点の実績と比較（年度途中の暫定値） | +0.41% |

実運用は、所得・控除を推計する誤差も含む条件である。それでもテスト年と同程度の誤差に収まり、検証で見積もった精度が実運用でも再現された。ただし1年分の結果のため、今後も年ごとに確認する。

全指標・検証条件は、末尾の「詳細」を参照。

## 設計の判断

| 観点 | 判断 | 業務の知識による理由 |
|---|---|---|
| モデルの選定 | LightGBM（勾配ブースティング木） | 住民税は、所得控除や非課税基準によって「ある金額を境に切り替わる」階段状の計算になる。決定木はこれをそのまま表現でき、データの前処理も少ない。異動のある職場で引き継げるよう、シンプルに保った。 |
| 所得の特徴量 | 合計所得は重なりのない所得区分だけを足して作る。控除合計と、控除率・課税標準率も加える | 同じ所得でも控除の特性によって税額が大きく変化するため、フラグの追加や所得と控除の比率を追加した。 |
| 翌年の所得控除 | 「前年の実績＋制度改正による差」で更新する。コード値で持っている控除は、住民税の控除額表で金額に換算する（実データ版） | 扶養・配偶者などの控除は人ごとに続くものなので、前年の値を引き継ぐ形を保った。 |
| 評価指標 | 主指標は集計誤差率（税収合計の誤差）。個人単位の誤差は補助に使う。 | 自治体の予算に必要なのは、個人の税額ではなく税収の合計のため、合計の精度を優先した。 |
| 税法のルール | 非課税判定（地方税法295条）は予測のあとにルールで0円に上書きする。法律で決まる値は年度別の表に、期間限定の補正はルールの一覧に分ける | 法律で決まることはモデルに推測させない。恒久的な改正と、定額減税のような期間限定の補正とは、性質が異なるため外部で管理。 |

---
## 限界と今後の課題

- 過去6年はいずれも上昇トレンドのため、トレンドが崩れた年や大きな税制改正の年に同じ精度が出るかは未検証。
- 予測では対象者を前年と同じとしており、転入・転出・死亡は反映していない（ダミーで試算したが改善せず、実データは検証中）。
- 高額所得者の細分化（所得の種類ごとの翌年の継続率など）による精度の向上。
- 精度を上げる一方で、職員間の引き継ぎを考え、データの加工は必要最小限にとどめる。

### 所見

- ダミーのウォークフォワード検証（fold1〜4）は、すべて誤差率±0.1%以内・個人MAPE 1.4〜1.7%に収まり、安定している。
- ダミーの精度（R² 1.000）が高いのは、ダミーの税額を、特徴量に含まれる課税標準額などから同じ計算式で作っているため。実データは控除の持ち方や特定区間の偏り・外れ値があり、同じ精度にはならない。データ加工の流れは自治体ごとに検証する必要がある。
- 実データは個人単位の誤差が大きいが、本プロジェクトの目的である税収合計の精度（集計誤差率）は、ダミーと同等に保てている。
- 実データでは高額納税者を学習時に上限でクリップしたため、`05`の予測合計がやや小さめに出る。ただし、高額所得が単年で終わる可能性や、転出・死亡で翌年の税額が0円になる可能性を考えると、前年の値をそのまま使うよりリスクを抑えられる。

### CLI のオプション

各ステップの役割は「[処理の流れ](#処理の流れ)」、入出力ファイルは「[ファイル構成](#ファイル構成)」を参照。

| `05_predict_2026.py` | `--growth {auto,table,none}` | 伸び率の方式（「[予測の伸び率を指定したいとき](#予測の伸び率を指定したいとき春闘年金改定率など)」） |

- `year` は特徴量に含めない（木モデルは学習範囲外の年を外挿できないため）。予測年の所得の伸びは`05`の外挿で与える。

<summary><b>設定値の変更ガイド（年度の更新・伸び率・税制改正・特徴量）</b></summary>

### 設定値の変更ガイド

設定値はすべて`02_src_py/`の原本を編集する（公開用の`03_notebooks/`へはコピーで反映する）。

#### 設定ファイルの構成

**`config.py`**：運用で決める値を集約する。法律・条例で決まる値（均等割・非課税基準など）は`tax_reform.py`にある。

| 設定グループ | 主な設定項目 |
|---|---|
| 年度 | `TRAIN_YEARS`, `TEST_YEAR`, `PREDICT_YEAR` |
| モデル・検証 | `LGBM_PARAMS`, `VALIDATION_MODE`, `CONFORMAL_COVERAGE` |
| 予測の伸び率（05） | `GROWTH_SOURCE`, `FORECAST_GROWTH_TABLE`, `WAGE_RATE_OVERRIDE` |
| 税額控除の推計（05） | `FURUSATO_PARAMS`, `HOUSING_PARAMS` |
| ダミー生成（01） | `N_PER_YEAR`, `TURNOVER_RATE`, `POPULATION_GROWTH_RATES`, `AGE_WEIGHTS`, `GENDER_RATIO`, `SALARY_GROWTH_RATES`, `PENSION_GROWTH_RATES` |

**`tax_reform.py`**：法律・条例で決まる値と計算、税制改正の補正ルールを持つ共通モジュール。

| 部分 | 内容 |
|---|---|
| 年度別の表（冒頭） | 均等割・非課税基準・給与所得控除の最低額・住宅ローン控除の上限など。改正されたら施行年度の行を足す。均等割と非課税基準は自治体固有の値 |
| `compute_*` 関数 | 給与所得控除・公的年金等控除・基礎控除・非課税判定（地方税法第295条）などの計算 |
| `REFORMS`（末尾） | 期間限定の補正と、`06`の集計補正。`active`で切り替える（現在はすべて無効）。書き方は「[税制改正に対応したいとき](#税制改正に対応したいとき)」 |

#### 年度を更新したいとき

毎年の運用で必ず行う。`config.py`の年度を1年ずつ進める。

```python
# config.py
TRAIN_YEARS  = [2020, 2021, 2022, 2023, 2024, 2025]  # 訓練年を追加
TEST_YEAR    = 2026                                   # テスト年を更新
PREDICT_YEAR = 2027                                   # 予測年を更新
```

あわせて次を確認する。

1. 税制改正があった年度は、`tax_reform.py`冒頭の年度別の表に施行年度の行を足す（「[税制改正に対応したいとき](#税制改正に対応したいとき)」）。
2. 伸び率の方式を table にしている場合は、`FORECAST_GROWTH_TABLE`に新しい予測年度の値を足す（欠けているとエラーで止まる）。
3. ダミーデータを作り直す場合は、`POPULATION_GROWTH_RATES`・`SALARY_GROWTH_RATES`・`PENSION_GROWTH_RATES`に新しい年を足す。

#### 予測の伸び率を指定したいとき（春闘・年金改定率など）

`05`が直近年の所得を伸ばすときの伸び率は、既定では実績から自動で決める。外部の値を使うとき、または伸ばさないときは次のように指定する。

| 方式 | 指定方法 | 内容 | `06`の自動のトレンド補正 |
|---|---|---|---|
| auto（既定） | `config.py`の`GROWTH_SOURCE = "auto"` | 実績の全員平均の直近2年の伸び率（給与・年金・事業所得） | 掛ける |
| table | `GROWTH_SOURCE = "table"`または`--growth table` | `FORECAST_GROWTH_TABLE`の値（給与・年金。事業所得は自動） | 掛ける |
| none | `GROWTH_SOURCE = "none"`または`--growth none` | 伸び率0%（直近年の所得のまま） | 掛けない |
| 直接指定 | `--wage-rate 0.0525`・`--pension-rate 0.019`（上乗せは`--wage-delta`） | 方式より優先する | 掛けない |

```python
# config.py（キーは住民税の年度、値は前年の所得の伸び率。例: 2026年度 ← 2025年の春闘）
GROWTH_SOURCE = "table"
FORECAST_GROWTH_TABLE = {
    "給与収入":          {2022: ..., 2023: ..., 2024: ..., 2025: ..., 2026: ...},
    "雑収入_公的年金等": {2022: ..., 2023: ..., 2024: ..., 2025: ..., 2026: ...},
}
```

- table では、予測年度に加えて過去年検証の年度（2022〜2025）の値も要る。`06`の乗率と信頼区間は、2026年度の予測と同じ方式で行った過去年検証から作るため。
- 方式を変えたら、`05`を`--no-backtest`なしで実行し直す（方式が一致しないと`06`は自動の乗率を掛けず、理由を表示する）。
- 使った方式と伸び率は`05out_prediction_summary_YYYY.csv`に残る。表の値は既定で空で、実際の値と出典は運用で決める。

全く補正しない場合は、`05 --growth none`と`06 --no-trend`を組み合わせる（税制改正の補正は既定で無効）。

#### 税制改正に対応したいとき

改正の種類によって書く場所が違う。同じ改正を両方に書くと二重に適用される。

| 改正の種類 | 書く場所 | 例 |
|---|---|---|
| 恒久的な改正（金額・基準が変わる） | `tax_reform.py`冒頭の年度別の表に、施行年度の行を足す | 給与所得控除の最低額（2026年度〜65万円）、均等割、非課税基準 |
| 期間限定の補正、個人データでは表せない改正 | `tax_reform.py`末尾の`REFORMS`に辞書を1つ足す | 定額減税（2024年）、扶養要件の引き上げ（`06`の集計補正） |

`REFORMS`に足すときの手順:

1. 新しい計算が必要な場合だけ、`tax_reform.py`に補正関数（`_apply_<name>`）を書く。
2. `REFORMS`に辞書を1つ足す。

```python
{
    "name": "teigaku_reduction",          # 識別子
    "func": _apply_teigaku_reduction,     # 補正関数（06 の集計補正は None）
    "reform_type": "label_correction",    # 04で学習ラベル / feature_correction=05で特徴量 / macro_correction=06で集計値
    "effective_year": 2024,               # 施行年度
    "one_time": True,                     # True=施行年のみ
    "active": False,                      # False なら補正しない
    "params": {"amount_per_person": 10_000},
    "memo": "備考",
},
```

3. `uv run python 02_src_py/tax_reform.py`を実行し、記録（`models/tax_reform_snapshot.json`）を更新する（忘れると`04`が警告する。結果には影響しない）。

#### 特徴量を追加・削除したいとき

モデルに使う列は`config.py`の2つの一覧で管理し、`FEATURE_COLS`はその2つをつないだもの。

```python
# config.py
RAW_FEATURE_COLS = [...]        # 元データにある列のうち、モデルに使うもの
GENERATED_FEATURE_COLS = [...]  # 03_feature_eng.py の preprocess() が作る列
FEATURE_COLS = RAW_FEATURE_COLS + GENERATED_FEATURE_COLS
```

| やりたいこと | 直す場所 |
|---|---|
| 元データにある列を使う・外す | `RAW_FEATURE_COLS`に書き足す・消す |
| `03`で新しい列を作る | `preprocess()`に処理を書き、`GENERATED_FEATURE_COLS`にも同じ列名を書き足す |
| `03`で作っている列を外す | `preprocess()`の処理と`GENERATED_FEATURE_COLS`の両方から消す |

- `03`は、`GENERATED_FEATURE_COLS`と実際に作った列がずれているとエラーで止まる（片方だけの直し忘れを防ぐため）。
- 変更後は`03`→`04`→`05`を実行し直す。

### 注意事項

- GitHubで公開しているのはダミーデータ版であり、掲載している実データの検証結果は、精度を示す比率の指標（集計誤差率・WMAPE・MAPE・R²）のみを示している（金額・人数・件数・伸び率など規模を推測できる値は非公開）。実際の税収予測に使用する際は、実データによる再学習と十分な検証を行うこと。
- 住民税の計算式は自治体・年度によって一部異なる場合がある（級地区分による非課税ラインの違い、均等割の超過課税等）。ダミー版は所得割の標準税率（10%）、1級地の非課税範囲、超過課税を含む均等割（5,300円）を前提としている。自治体に合わせるときは`tax_reform.py`冒頭の年度別の表を直す。
- 個人情報を含む実データを扱う場合は、データの取扱いポリシーに従う。実データについてはGitHubには公開しない。また、ダミーデータについても生成csvは容量の関係から`.gitignore`対象とする。

主要ライブラリ：`lightgbm`, `pandas`, `numpy`, `scikit-learn`, `scipy`（合計の信頼区間の t 分布）, `matplotlib`, `jupyter`。Python 3.14以上を想定（`.python-version`参照）。
